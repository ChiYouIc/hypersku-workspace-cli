第一个，上下文爆炸。7.5k 到 1.5w token 常驻，三重代价：直接的钱、挤占任务可用的窗口、还有更隐蔽的注意力稀释——模型要在 50 段描述里找出"这一个"，每次推理都在噪声里跋涉。

● SOLUTION · 一个转向

从 选工具 到 调命令

灵感来自钉钉（dws）/ TAPD（tapd-ai-cli）的"命令入口 + 技能文档"形态，在 hypersku-cli 试验场验证。

💡 关键洞察：命令行的帮助是内省的、分层的、按需的。你不会在登录时被灌输全部 50 个子命令。
人类从来不需要把 CLI 手册背进脑子，为什么模型需要？
🎯 交互方式改变：从"让模型在工具列表里选"，变成"让模型调用命令"。

先交代真实的三步演进：MCP 多工具断续用了一年多，description 之痛慢慢积累；然后花几个月做了 Go CLI 试验场；最后一个月内收束成 Command Pattern。不是先想好模式再找应用，是每一步都被上一步的痛点推着走。

第二步值得展开。被 description 折磨久了，某天突然想到：我们日常给 Agent 用的第三方平台——钉钉 dws、TAPD tapd-ai-cli——不都是"一个命令行入口加一份按需加载的技能文档"的形态吗？查证后确认：命令加技能包是被多个第三方平台验证过的做法。于是用 Go 加 Cobra 开发了 hypersku-cli，覆盖同样的 14 个业务域。它不是生产工具，是试验场——在本地快速验证命令的形态、稳定性与可用性，skill 也先对着 CLI 编写和测试。

命令行有个被严重低估的特性：帮助是内省的、分层的、按需的。你敲 hypersku-cli --help，看到的是一张能力版图；进入某个域再看第二层；具体命令 --help 才看参数。三层帮助，每层只在需要时看一眼，看完就走。

于是那个问题浮出来了：人类从来不需要把 CLI 手册背进脑子，为什么模型需要？

关键洞察是：命令是比工具更自然的抽象。工具的协议形态要求一次性全暴露；命令的使用形态天然支持按需发现。交互方式就此改变——从"让模型在工具列表里选"，变成"让模型调用命令"。就这一个转向，后面所有设计都从这里推出来。

💡 正名：不是 CLI，不是 shell 封装——是应用内的 Command Pattern。一条命令 = 一个 Java 方法调用，没有 Runtime.exec，没有字符串拼接，shell 元字符没有语义生存空间。

最终方案是个三件套。

第一，MCP 收敛为单一工具 run_cli：一个 string 参数，一段固定说明，schema 恒定，上下文占用从 O(N) 降到 O(1)。

第二，16 个 skill 做可见性路由：1 个总览技能常驻作路由索引，15 个域技能按能力域划分、场景命中才注入，每个域 0.5 到 1k token，在合适的时机告诉模型"这个域有哪些命令"。

第三，Command Registry 做能力载体：服务端进程内的一棵命令树，命令名到方法调用的映射。

这里要正名，因为看到 run_cli 这个名字，很容易误会我们在 MCP 里包了一个 shell。不是：不 fork 进程，命令执行是进程内的方法调用；不拼 shell 字符串，输入被 tokenizer 按空白切分、按选项语法解析成结构化 Map——分号、管道、$() 这些 shell 元字符在这里没有语义生存空间。它是应用内的 Command Pattern。

还有个彩蛋：同一套命令语法有两个宿主——Go CLI 做试验场，验证命令稳定性与可用性、编写测试 skill；Java 命令层做生产，服务 MCP。命令先在 CLI 上打磨，再固化到 Java 侧，一套心智，两处复用。

● PATTERN · 应用内的 Command Pattern

一条命令 = 一个对象

📖 GoF 意图：将请求封装为对象，从而可以用不同的请求对客户进行参数化，并支持请求的排队、日志记录与可撤销操作。
模式角色职责本方案对应
Command把请求封装成对象CommandDefinition（execute 即 run 函数字段）
ConcreteCommand具体命令实现各 CommandProvider 产出的命令定义
Invoker持有并触发命令分发器 evaluate()（tokenize + 分发）
Receiver真正干活的人领域 Service / 业务 API
Client创建并装配命令CommandProvider 实现 + ShellConfig
💡 判据：调用者与接收者解耦——分发器对任何业务 Service 一无所知。经典收益逐一兑现：请求参数化、日志记录、排队治理；主动裁剪 undo。subCommands 是 Composite 组合；自描述元数据 + --help 内省，是对教科书版的扩展。

既然标题叫 Command Pattern，花两分钟把模式本身讲清楚，也算正名。

命令模式是 23 个经典设计模式之一，GoF 的意图一句话：将请求封装为对象，从而可以用不同的请求对客户进行参数化，并支持请求的排队、日志记录与可撤销操作。五个固定角色跟我们的实现一一对应：CommandDefinition 就是 Command，execute 就是那个 run 函数字段；各 CommandProvider 产出的是 ConcreteCommand；分发器 evaluate 是 Invoker；领域 Service 是 Receiver；CommandProvider 加 ShellConfig 是 Client。

判断"是否命令模式"的标志是调用者与接收者解耦：分发器对任何业务 Service 一无所知，只面对统一的命令抽象。模式承诺的经典收益逐一兑现：请求参数化——模型用命令字符串参数化调用；日志记录——单入口一行审计日志；排队与治理——命令级限流的架构前提。唯一主动裁剪的是 undo，查询型命令无状态可撤。

两个加分项：subCommands 命令树是命令模式与 Composite 模式的经典组合；而给命令对象挂上 description、options、arguments 这些自描述元数据、支撑 --help 内省，是我们对教科书版的扩展——命令从"可执行"升级为"可自我解释"，L2 的运行时内省完全建立在这个扩展上。

● ARCH · MCP 收敛为单工具

run_cli 的设计

// CliTools.java — 唯一的 MCP 工具入口
@Service
@PreAuthorize("hasAuthority('tool:cli')")
public class CliTools {

    @McpTool(name = "run_cli", title = "执行 CLI 命令", description = """
        通用命令行工具入口，执行 Hypersku CLI 命令。
        所有命令必须以 `hypersku-cli` 开头，语法：
        `hypersku-cli <命令路径> [位置参数] --<选项>=<值>`""")
    public String runCli(@McpToolParam(description = "命令") String cliCommand) {
        if (StrUtil.isBlank(cliCommand)) return shell.help(); // 空命令 → 总帮助
        logger.info("run command: {}", cliCommand);
        return this.shell.evaluate(cliCommand);
    }
}

schema 恒定
O(N) → O(1)

单参数有意为之

利用模型的命令行
语料先验

空命令 = 路标

返回总帮助
零成本兜底

先看 run_cli 的代码，很短，值得逐行看。

类上挂 @PreAuthorize("hasAuthority('tool:cli')")——授权落点第四章细讲。工具方法就一个：@McpTool 注解声明名字和描述，description 里只写了命令语法规范——必须以 hypersku-cli 开头、位置参数在选项前、任意命令加 --help 看帮助。注意这段描述是恒定的，不含任何具体命令知识。

三个设计要点。第一，为什么是 1 个而不是 N 个：一个 string 参数吃下所有命令，schema 恒定、不随能力增长变化，上下文从 O(N) 降到 O(1)。当然，少数强 schema 工具我们保留了原生 MCP 形态，混合策略在第八节讲。

第二，单参数是有意为之：不做结构化的 command 加 args 对象，因为命令语法本身就是模型的已知心智——全世界的模型都练过海量命令行语料，--help 是它们最熟悉的内省动作。把命令当字符串，是把这个先验直接拿来用。

第三，空命令返回总帮助：模型迷路时有一个零成本的"回到路标"动作。中间那行 logger.info 后面审计部分会用到，先记住它。

💡 重要区分：skill 只控制"模型看得见什么"，是纯粹的可见性问题。skill ≠ 权限——技能包被注入不等于执行权被授予，真正的边界在第四章。

第二层，skill 做可见性路由。它回答一个问题：模型在某个场景下，应该知道哪些命令的存在？

run_cli 的描述不承载任何具体命令知识，命令知识的注入由 16 个技能包承担：一个总览技能，只放一张"能力域到命令入口到技能包"的路由表；下面 15 个域技能，各管一个域的命令细节。触发靠 frontmatter description 的描述式路由——写的是"用户会说的话"，比如"当用户提到物流、轨迹、快递、到哪了、包裹并提供运单号时"。宿主按语义命中，除常驻的总览路由外，只有被命中的域技能进入上下文。

这形成四级渐进式披露。L0 是 run_cli，常驻上下文约 100 token，恒定。L1 是总览加域技能包：总览技能常驻作路由索引，约 500 token，只放一张能力版图表；域技能场景命中时注入，每个 0.5 到 1k token，同时激活的域通常不超过两三个。L2 是 --help 运行时内省，按次返回不驻留。L3 是命令执行结果，进入对话。能力知识从常驻 prompt 变成按需取用，每一级只在需要时付费。

最后强调一个区分：skill 不等于权限。它只控制模型看得见什么。技能包被注入不等于执行权被授予；反过来，模型没见过某个命令也不构成安全边界——它可能从对话历史里学到命令名并调用。真正的边界在第四章，马上到。

● ARCH · command 做能力载体

Command Registry

// 一命令一方法，进程内执行
public class CommandDefinition {
    String name;                                        // 命令名
    String shortDesc; String description;               // help() 的素材
    Function<Map<String, String>, String> run;          // 执行函数
    Map<String, CommandDefinition> subCommands;         // 子命令树
    List<OptionDefinition> options;                     // --key=value
    List<ArgumentDefinition> arguments;                 // 位置参数
}

// 注册：新增命令只需新增一个类
@Configuration
public class ShellConfig {
    public ShellConfig(List<CommandProvider> providers) {  // Spring 自动扫描
        Shell.builder().commands(providers.stream()
            .map(CommandProvider::command).toList()).build();
    }
}
💡 新增命令 = 新增一个类，注册代码零改动，符合开闭原则。执行是进程内方法调用，没有 Runtime.exec，没有字符串拼接进 shell。

第三层，Command Registry——一棵由 CommandDefinition 组成的命令树（代码里的 Shell 是历史类名，实为命令注册与分发容器，非 shell）。

看字段：name 是命令名；shortDesc 和 description 是帮助文本的素材；run 是执行函数——一命令一方法；subCommands 是子命令树，域内细分靠它承载；options 是选项参数，arguments 是位置参数，按声明顺序自动编号。

注册机制是 CommandProvider 函数式接口：每个实现类是一个 Spring 组件，提供一条子命令；ShellConfig 注入 List 自动聚合成树。新增命令等于新增一个类，注册代码零改动，符合开闭原则。

执行流程：evaluate 按空白 tokenize，根命令名强校验——写错直接返回总帮助，模型拿到的错误信息本身就是路标；子命令逐级分发；--help 在任意位置都能触发；位置参数在前、--opt=value 在后，解析成 Map 交给执行函数。这里有个隐性红利：面向模型的文档只教一种范式，但解析层其实同时兼容 --opt=value、--opt value 和 --flag 三种形式——模型偶尔写串也不会失败。范式收敛是给模型减负，不是给系统加脆性。

校验也是分层的：解析层做结构性校验——必填项、选项名合法性、位置参数个数；方法层做业务校验——订单号格式、数据归属。校验失败不抛异常栈，返回 help 或一句"缺少必填参数 trackingNumber"——模型读得懂，就能自我修正。

💡 三层分离的本质：可见性、授权、执行各自独立演进——加命令不动 MCP 层，调路由不动命令，改权限不动前两者。

为什么这个分层成立？三层各管一件事，职责单一且正交：MCP 工具层管入口和协议，回答"模型怎么调"，几乎不变；skill 层管可见性路由，回答"模型此刻该知道什么"，随场景演进；command 层管能力和执行，回答"实际能做什么"，随业务增长。

对比 MCP 多工具方案就清楚了。在那边，可见性、授权、执行全部焊死在同一个 @McpTool 注解里：你想对某个客户端隐藏一个工具？严格说不是做不到，而是没有声明式的做法——协议把工具清单定在 server 粒度，Spring AI 注解模式注册即全量暴露，真要区分只能按客户端拆部署。而改一个参数说明，则是全量客户端的 prompt 同步变化。

三层分离后，每件事都可以独立演进：加命令不动 MCP 层，调路由不动命令，改权限不动前两者。

审计也顺带受益。run_cli 的入口收敛让全系统的执行流只有一个咽喉要道，一行 logger.info 记录的就是"执行了什么"——命令加参数；"谁"和"何时"在同一请求上下文里对齐。审计要素天然聚合在一处，多工具方案的同样要素要横跨 N 个工具分散埋点。

💡 三层权限模型：
skill → 可见性（模型知道什么）— 不是安全边界
command → 授权（允许执行什么）— Spring Security authority
method → 执行（真正干活）— 领域 Service 业务校验

进入第四章，权限模型。很多人听到"命令"会警惕：这是不是给了模型一个 shell？恰好相反，应用内 command 的权限边界比任何 OS shell 都清晰。

三个"没有"。没有 shell，就没有 shell 注入——分号、管道、反引号在这里只是普通字符，tokenizer 按空白切分后进入 Map，注入语法没有可执行的落点。不 fork 进程，就没有逃逸——没有子进程就没有进程逃逸、没有环境继承、没有任意二进制执行，执行面收敛为注册表里那几个 Java 方法。不是复用 OS 权限，而是完全自主——边界定义在应用内部，这反而让它可以做到 OS 做不到的粒度，下一页讲。

权限模型是三层：skill 管可见性，模型知道什么——注意这不是安全边界；command 管授权，允许执行什么——落在 Spring Security authority；method 管执行，真正干活——领域 Service 里的业务校验。

授权的具体落点在工具类上：CliTools 挂 hasAuthority('tool:cli')，OrderInfoTools 挂 tool:customer。API Key 跟 authority 绑定——配置里每个 key 映射一组 authority，key 一进来，能执行哪些工具组就定了。模型"看得见"和"被允许"是两条独立的轴。

● PERMISSION · shell 做不到的粒度

命令树上的任意子树

1

方法级授权

每条命令可挂独立 authority，粒度到单条命令（写操作收紧为未来预留）

2

参数级授权

拦截器拿到解析后的 Map，按参数值做策略（如只查自己 tenant 的订单）

3

上下文级授权

请求所在的会话、用户、来源 key 全部在 Spring 上下文里，方法执行时随手可取

4

组合级授权

允许 logistics tracking 但禁止 after-sales 域——OS 只能给整个可执行文件，我们能给命令树上任意子树

💡 权限拒绝反馈给模型：拒绝发生在 Spring Security 过滤器层，返回结构化的"权限不足"消息（非裸 500）。模型收到后停止重试、向用户解释——因为这是明确的"不允许"，不是"参数错了再试一次"。

因为命令执行就是方法调用，方法级的一切控制手段都直接可用。先说现状：当前落地的是工具组级授权——@PreAuthorize 加 key 到 authority 的映射。下面四种粒度是这套架构顺手可得、按需启用的。

方法级：每条命令的执行函数可以挂独立 authority，查询类放行——未来若引入写操作，可设独立的高敏 authority 收紧，粒度到单条命令（当前业务全部为 query）。参数级：拦截器能拿到解析后的参数 Map，可以按参数值做策略，比如某些 key 只能查自己 tenant 的订单前缀。上下文级：会话、用户、来源 key 都在 Spring 上下文里，方法执行时随手可取。组合级：允许 logistics tracking 但禁止 after-sales 域整体——OS 只能给你整个可执行文件，我们能给命令树上任意一棵子树。

再补一条对抗 prompt injection 的防线：恶意网页或对话历史能诱导模型"看见"甚至尝试调用某条命令，但不会让 authority 多放行一个组。可见性可能被注入操纵，准入不会。这就是两层必须分离的原因。

实战细节：权限拒绝的反馈要面向模型设计。第一版返回裸 403，模型会固执地重试或换参数硬闯。改成结构化的"该 key 无权执行此命令组"后，模型从重试转为转告用户——因为这是明确的"不允许"，不是"参数错了再试一次"，对话体验好了很多。

● BOUNDARY · 不是银弹

临界点：命令与工具的分工

长任务 / 流式输出

命令是请求-响应式的，分钟级任务与渐进式结果装不进"一次调用一个字符串返回"，需任务句柄 + 轮询/订阅补足。

重外部资源操作

多步确认、断点续传、大文件——复杂交互协商更适合原生工具或专用协议。

写 / 编辑类能力

当前全部为 query，无 modify 实践。初步推断不适合：错误成本不对称、解析层校验弱于 schema；但 modify 难点对原生工具同样成立。

复杂 schema 场景

十几个强类型参数、嵌套结构、严格枚举——schema 约束比字符串命令更稳。混合保留 LogisticsTools 等原生工具。

💡 立场：不是全盘否定传统工具调用，而是寻找临界点、按场景分而治之——命令与工具不是替代关系，是分工关系。

诚实说清边界，这套模式不是银弹。先亮立场：我们不是用命令模式全盘否定传统工具调用，而是在找两种方式的临界点——哪种能力用命令承载，哪种留给原生工具，按场景分而治之。

四类不适合。长任务和流式——命令是请求响应式的，分钟级任务和渐进式结果装不进一次调用一个字符串返回，要任务句柄加轮询订阅补。重外部资源——多步确认、断点续传、大文件，更适合原生工具或专用协议。

写编辑类要重点说：先交代事实——因为业务原因，我们目前所有工具都只做 query，没有 modify 实践，下面是基于历史经验的初步推断，不是结论。推断 command 可能不适合：查询错了代价至多一次重试，编辑错了脏数据可能已经落库，字符串命令在解析层的结构校验也弱于 schema 的类型枚举必填约束。但另一半也要说清：modify 的难点——复杂表单项、严格校验、多轮交互、多步处理——是场景本身的挑战，对直接用 MCP 工具同样成立，不是换回原生工具就能解决。

复杂 schema——十几个强类型参数、嵌套结构、严格枚举，schema 约束反而比字符串命令稳。我们的做法是混合保留：CliTools 之外，LogisticsTools 这些少数强 schema 工具仍以原生 MCP 形态存在。命令与工具不是替代关系，是分工关系。
