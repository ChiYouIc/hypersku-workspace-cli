● PROBLEM · 连锁反应

三个连锁问题

① 上下文爆炸

50 schema ≈ 1w~1.5w token 常驻。三重代价：直接费用、挤占窗口、注意力稀释

② 选择噪声

"订单到哪了" → 模型在 3 个"查询物流"工具间摇摆。description 看起来全都一样。

③ 扩展摩擦

加一个工具 = 加 schema + 加上下文 + 全列表辨识度重排。description 越写越"卷"。

💡 真实翻车现场：用户问"订单到哪了"，模型把客户订单号当快递运单号，传给了 domestic_logistics_query——从 description 看，它们都"查询物流"。

这三个问题是连锁反应。上下文爆炸是最直接的：1 万多 token 常驻 prompt，直接的钱、挤占窗口、注意力稀释——模型要在 50 段描述里找出"这一个"。

选择噪声更隐蔽。我们真实翻车过：用户问"订单到哪了"，模型在三个"查询物流"工具之间摇摆——客户订单物流、快递单号轨迹、采购物流。从 description 看，它们确实都叫"查询物流"。人类工程师都会混淆两个同名函数，模型也一样。

扩展摩擦是个恶性循环。你越加工具，description 越写越长、越写越"卷"来互相区分，而每一段辩解式描述又反过来加重上下文问题。加一个工具的边际成本越来越高。

💡 正名：不是 CLI，不是 shell 封装——是应用内的 Command Pattern。一条命令 = 一个 Java 方法调用，没有 Runtime.exec，没有字符串拼接，shell 元字符没有语义生存空间。

最终方案三件套。第一，MCP 收敛为单一工具 run_cli，一个 string 参数，schema 恒定，上下文占用 O(1)。

第二，16 个 skill 做可见性路由。每个 skill 按能力域划分，在合适时机告诉模型"这个域有哪些命令"。场景命中时才注入，每个域 0.5 到 1k token。

第三，Command Registry 做能力载体。命令执行是进程内的方法调用，Function 挂在 Map 上。这里要强调：这不是 CLI 封装。没有 fork 进程，没有拼 shell 字符串。分号、管道、反引号这些 shell 元字符在这里没有语义生存空间——输入被 tokenizer 按空白切分，命令语法在解析层就终结了。

● ARCH · MCP 收敛为单工具

run_cli 的设计

// CliTools.java — 唯一的 MCP 工具入口
@Service
@PreAuthorize("hasAuthority('tool:cli')")
public class CliTools {

    @McpTool(name = "run_cli", title = "执行 CLI 命令", description = """
        通用命令行工具入口，执行 Hypersku CLI 命令。
        所有命令必须以 `hypersku-cli` 开头，语法：
        `hypersku-cli <命令路径> [位置参数] --<选项>=<值>`""")
    public String runCli(@McpToolParam(description = "命令") String cliCommand) {
        if (StrUtil.isBlank(cliCommand)) return shell.help(); // 空命令 → 总帮助
        logger.info("run command: {}", cliCommand);
        return this.shell.evaluate(cliCommand);
    }
}

1 个 vs N 个

schema 恒定
O(N) → O(1)

单参数有意为之

利用模型的命令行
语料先验

空命令 = 路标

返回总帮助
零成本兜底

先看 run_cli 的代码。整个类只有一个 MCP 工具方法，一个 string 参数。为什么是 1 个而不是 N 个？一个 string 参数吃下所有命令，schema 是恒定的，不随能力增长变化。

为什么不用结构化的 command 加 args 对象？因为命令语法本身就是模型的已知心智——全世界的模型都练过海量命令行语料，--help 是它们最熟悉的内省动作。把命令当字符串，是把这个先验直接拿来用。

另一个细节：空命令返回总帮助。模型迷路的时候，有一个零成本的"回到路标"动作。

● ARCH · command 做能力载体

Command Registry

// 一命令一方法，进程内执行
public class CommandDefinition {
    String name;                                        // 命令名
    String shortDesc; String description;               // help() 的素材
    Function<Map<String, String>, String> run;          // 执行函数
    Map<String, CommandDefinition> subCommands;         // 子命令树
    List<OptionDefinition> options;                     // --key=value
    List<ArgumentDefinition> arguments;                 // 位置参数
}

// 注册：新增命令只需新增一个类
@Configuration
public class ShellConfig {
    public ShellConfig(List<CommandProvider> providers) {  // Spring 自动扫描
        Shell.builder().commands(providers.stream()
            .map(CommandProvider::command).toList()).build();
    }
}
💡 新增命令 = 新增一个类，注册代码零改动，符合开闭原则。执行是进程内方法调用，没有 Runtime.exec，没有字符串拼接进 shell。

第三层是 Command Registry——一棵由 CommandDefinition 组成的命令树。每条命令对应一个 Function，接收解析后的参数 Map，返回字符串。

命令注册靠 CommandProvider 函数式接口，每个实现类提供一条命令，ShellConfig 注入 List 自动扫描聚合成树。新增命令只要新增一个类，注册代码零改动。

执行是进程内方法调用。evaluate 方法按空白 tokenize，根命令名强校验防止跑偏，子命令逐级分发。--help 任意位置触发帮助。命令语法在解析层终结，之后全是类型安全的 Java 方法调用。

● ARCH · 为什么分层成立

三层正交 vs MCP 多工具

我们的三层架构MCP 多工具方案

💡 三层分离的本质：可见性、授权、执行各自独立演进——加命令不动 MCP 层，调路由不动命令，改权限不动前两者。

为什么这个分层成立？三层各管一件事，职责单一且正交。MCP 工具层管入口和协议——模型怎么调？skill 层管可见性路由——模型此刻该知道什么？command 层管能力和执行——实际能做什么？

对比 MCP 多工具方案。在那边，可见性、授权、执行全部焊死在同一个 @McpTool 注解里。你想对某客户端隐藏一个工具，做不到；你想改一个参数说明，全量客户端的 prompt 同步变化。

三层分离后，每件事都可以独立演进：加命令不动 MCP 层，调路由不动命令，改权限不动前两者。审计也收敛了——run_cli 一个入口，logger.info 一行日志就是完整的审计事实。

💡 三层权限模型：
skill → 可见性（模型知道什么）— 不是安全边界
command → 授权（允许执行什么）— Spring Security authority
method → 执行（真正干活）— 领域 Service 业务校验

进入第四章：权限模型。很多人听到"命令"会警惕，是不是给了模型一个 shell？恰好相反，应用内 command 的权限边界比任何 OS shell 都清晰。

三个"没有"。没有 shell，分号、管道、反引号在这里只是普通字符，注入没有可执行的落点。不 fork 进程，没有逃逸、没有环境继承。不依赖 OS 权限，边界完全自主定义。

三层权限模型。skill 管可见性，是注意力分配问题，不是安全边界。command 管授权，通过 Spring Security authority。method 管执行，领域 Service 里的业务校验。这三层正交，各自独立。

● PERMISSION · shell 做不到的粒度

命令树上的任意子树

1

方法级授权

tool:cli 放行查询类，tool:admin 才放行写操作，粒度到单条命令

2

参数级授权

拦截器拿到解析后的 Map，按参数值做策略（如只查自己 tenant 的订单）

3

上下文级授权

请求所在的会话、用户、来源 key 全部在 Spring 上下文里，方法执行时随手可取

4

组合级授权

允许 logistics tracking 但禁止 after-sales 域——OS 只能给整个可执行文件，我们能给命令树上任意子树

💡 权限拒绝反馈给模型：拒绝发生在 Spring Security 过滤器层，返回结构化的"权限不足"消息（非裸 500）。模型收到后停止重试、向用户解释——因为这是明确的"不允许"，不是"参数错了再试一次"。

因为命令执行就是方法调用，方法级的一切控制手段都直接可用。四种粒度：方法级，单条命令可以挂独立的 authority；参数级，拦截器能拿到解析后的参数 Map；上下文级，请求的会话、用户、来源 key 随手可取；组合级，可以定义命令树上任意一棵子树的权限——这是 OS 做不到的。

还有一个实战细节：权限拒绝的反馈要面向模型设计。第一版我们返回裸 403，模型会固执地重试。改成结构化的"该 key 无权执行此命令组"后，模型从重试转为转告用户，对话体验好了很多。

收尾。核心原则就一句话：上下文是稀缺资源，能力的加载应该是按需、分层、场景驱动的。多工具方案的失败不是工具太多，而是默认了"全部能力必须常驻上下文"。

我们做的就是把 Web 前端十年前就学会的事搬进 LLM 工程：路由懒加载。run_cli 是入口，skill 是路由表，--help 是运行时 introspection，命令树是代码分割后的模块。

这个原则不限于 MCP。RAG 的检索时机、Agent 的记忆加载、多 agent 的能力分配，都是同一个道理。
